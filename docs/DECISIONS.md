## 2026-07-18 — Pinned `react-dom` to `19.2.3` via npm `overrides`

`expo-router@57.0.7` depends on `@expo/ui` and `vaul` (web-only, used for an
internal `@expo/ui` web preview), which pull `react-dom@19.2.7` as a nested
dependency. That version peer-requires `react@^19.2.7`, conflicting with the
project's `react@19.2.3` (the version Expo SDK 57 itself expects — confirmed
via `npx expo install --check`, which reported `19.2.3` as correct once
pinned). Added:

```json

```

This is scoped to `react-dom` only, doesn't touch `react` or `react-native`,
and only affects the web bundling path (not used for the Android-primary
MVP). If a future phase adds real web support, revisit this pin.

`BUILD_SPEC.md` lists ESLint and Prettier as two separate required tools

entrypoint.

`BUILD_SPEC.md` section 13's repository structure lists `app.config.ts`

## 2026-07-18 — React Native Testing Library v14 `render()` is async

`@testing-library/react-native@14` made `render()` return a `Promise`
(internally wraps the initial render in `act`, required for React 19). Every
call site must `await render(...)` before using the returned queries;
calling it synchronously and reading `screen.getByText(...)` immediately
fails with "`render` function has not been called" because the render
hasn't resolved yet. Documented in `docs/TEST_PLAN.md` so Codex-authored
component tests don't hit this.

## 2026-07-18 — Added explicit `"types": ["jest"]` to `tsconfig.json`

`tsc --noEmit` couldn't see `describe`/`it`/`expect` globals in
`__tests__/**` even with `@types/jest` installed — `--listFiles` confirmed
`@types/jest/index.d.ts` wasn't being pulled into the program automatically,
while `@types/react` was. Root cause not fully isolated (suspect
interaction between `moduleDetection: "force"` and/or `moduleResolution:
"bundler"` in `expo/tsconfig.base` and typeRoots auto-inclusion under this
TypeScript version). Fixed pragmatically by adding
`"types": ["jest"]` to `tsconfig.json`'s `compilerOptions`. If more ambient
`@types` packages are added later and don't show up automatically, add them
to this array explicitly rather than re-debugging the root cause.

## 2026-07-18 — Timer badge convention: single floating badge, not per-cell repeated digit

Two conventions appeared across the approved screens: a single small
floating circular badge on one cell of a multi-cell timed piece
(`01-selection-preview`, `04-defuse-animation`, `05-defuse-success`,
`07-defuse-action`) vs. the same digit printed as plain text on every cell
of the piece (`02-invalid-placement`, `03-critical-countdown`,
`09-freeze-active`). Adopted the single-floating-badge convention: it's the
majority pattern among screens that show timed pieces, and it matches
`BUILD_SPEC.md` §6.11 literally ("Render the countdown on the visually most
suitable surviving cell, preferably the top-left surviving cell" — singular,
not "every cell"). Badge placement rule: the piece's topmost surviving
cell; leftmost among ties in that row. Affects the `TimerBadge` component
Codex will build in Phase 3/4 — see `docs/UI_IMPLEMENTATION.md` and
`docs/UI_REFERENCE_AUDIT.md` item 1.

## 2026-07-18 — Board width: 350px (Developer Handoff), not 380px (some gameplay screens)

`16-developer-handoff` (the authoritative design-token reference per the
ingestion task's precedence rule) declares a 390px reference viewport,
20px screen padding, and a 350px board width — internally consistent
(390 − 20×2 = 350). Several gameplay screens' inline CSS instead set the
board's `max-width` to 380px, which would leave only 5px of side padding
at the same 390px viewport. Resolved in favor of the Developer Handoff's
350px. In the actual RN implementation, board width is computed at runtime
from available screen width minus padding — neither 350 nor 380 is
hardcoded — but 350px is the reference value for parity checks against the
design. See `docs/STYLE_GUIDE.md` "Board geometry" and
`docs/UI_REFERENCE_AUDIT.md` item 7.

## 2026-07-18 — Added `urgentRed` (#FF003D) as a formal color token

`03-critical-countdown` and `14-tutorial-defuse` both use `#FF003D` for the
urgent (1-move) timer pulse, distinct from the existing `error` token
(`#FFB4AB`, used for invalid-placement feedback) — but neither the
Developer Handoff screen nor any other screen's declared color-token block
lists `#FF003D`. Decision: formalize it as a new `urgentRed` token rather
than folding it into `error`, so "invalid action" and "piece about to
explode" stay visually and semantically distinct — a player should never
confuse "you can't place that" with "this piece is about to explode."
Affects `docs/STYLE_GUIDE.md`'s color table and the `TimerBadge` component's
urgent-state styling.

## 2026-07-18 — Newly placed pieces may defuse themselves in the same turn

`BUILD_SPEC.md` §6.10 steps 5–6 ("identify timed pieces with no remaining
cells, award defuse bonuses") exclude nothing, so a piece whose own
placement completes lines covering all of its cells is defused immediately
at its full starting countdown (bonus `25 + 10 × countdown`). This rewards
deliberately finishing a line with the final piece and keeps the defuse
rule uniform — no special case for the just-placed piece. Covered by an
explicit test in `__tests__/domain/timedPieces.test.ts`.

## 2026-07-18 — Explosion penalty applied per expired piece

`BUILD_SPEC.md` §7.6 defines a 50-point explosion penalty but §6.12's
simultaneous-expiration rule doesn't say whether multiple same-turn
expirations cost 50 once or 50 each. Decision: one penalty per expired
piece (each emits "one explosion animation" per §6.12 and each is
independently the player's loss), with the score still floored at zero
after summing the whole turn's delta. Two simultaneous expirations
therefore cost 100. Combo resets once regardless of explosion count.

## 2026-07-18 — Power-up domain semantics not pinned down by BUILD_SPEC.md

Three small gaps resolved while implementing §6.15–§6.17; none change the
player-facing rules, only edge behavior:

1. **Freeze cannot be re-activated while active.** §6.16 allows two
   rewarded freezes per run but doesn't address stacking. Activating during
   an active freeze would waste a rewarded use (it would only top the
   counter back up to 2), so `activateFreeze` rejects while
   `freezeTurnsRemaining > 0`. The UI simply shouldn't offer it mid-freeze.
2. **Rewarded defuse ties break on earliest placement.** §6.17 requires
   deterministic tie resolution without naming a rule. Chosen: lowest
   `placedOnTurn` (the oldest piece), which is stable, explainable, and
   independent of object-key ordering.
3. **Rewarded defuse counts toward `piecesDefused` but scores nothing.**
   §6.17 grants no bonus points (unlike a line-clear defuse, §7.5), but the
   piece is genuinely defused, so it increments the stat that feeds the
   Bolts formula (§8.1). Revive re-checks game over after restoring the
   board: a run can, in principle, still be dead if the board is packed
   with normal blocks — the engine reports `gameOver` again rather than
   pretending the revive helped.
